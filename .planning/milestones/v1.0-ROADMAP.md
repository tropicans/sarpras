# Roadmap: Sarpras PPKASN

## Overview

Sarpras PPKASN will progress from a trustworthy migrated data foundation to secure administration and conflict-safe booking services, then expose those services through privacy-safe public requests and efficient administrative operations. Each phase adds a usable slice while keeping PostgreSQL as the authority for data integrity, authorization, and auditability.

## Phases

**Phase Numbering:**

- Integer phases (1, 2, 3): Planned milestone work
- Decimal phases (2.1, 2.2): Urgent insertions (marked with INSERTED)

## Phase Details

### Phase 1: Canonical Data & Migration

**Goal**: Establish the durable PostgreSQL data model and a repeatable, reconcilable migration path that preserves operational history.
**Mode:** mvp
**Depends on**: Nothing (first phase)
**Requirements**: DATA-01, DATA-02, DATA-03, DATA-04
**Success Criteria** (what must be TRUE):

  1. An administrator can run the legacy import repeatedly without duplicating records and with preserved source identifiers.
  2. An administrator can review a reconciliation report showing source, imported, rejected, and exception counts without credential exposure.
  3. Migrated booking history remains linked to its migrated asset and requester data.
  4. Every persisted booking date-time records its explicit Asia/Jakarta interpretation and normalized value.

**Plans**: 1 plan completed

### Phase 2: Secure Administration & Asset Setup

**Goal**: Give authorized staff a protected administration boundary and the ability to maintain the assets and schedules that can be booked.
**Mode:** mvp
**Depends on**: Phase 1
**Requirements**: AUTH-01, AUTH-02, AUTH-03, AUTH-04, ASSET-01, ASSET-02, ASSET-03
**Success Criteria** (what must be TRUE):

  1. An administrator can sign in with a migrated or newly provisioned email-and-password account and securely end that session by logging out.
  2. Every administrative read and mutation rejects an unauthenticated or unauthorized actor at the server boundary.
  3. An authorized administrator can deactivate an account and its active sessions no longer access administrative functions.
  4. An authorized administrator can create, edit, schedule availability for, close, and archive room or dormitory assets without erasing their historical records.

**Plans**: 3 plans completed
**UI hint**: yes

### Phase 3: Booking Integrity & Audit Core

**Goal**: Provide the authoritative lifecycle, conflict controls, and immutable event trail used by every booking command.
**Mode:** mvp
**Depends on**: Phase 2
**Requirements**: FLOW-01, FLOW-04, FLOW-05, OPS-03
**Success Criteria** (what must be TRUE):

  1. The system applies only explicit pending, approved, rejected, and cancelled booking states.
  2. Concurrent requests or approvals cannot create overlapping approved reservations for the same asset.
  3. Booking creation and approval recheck authoritative operating availability, closures, and reservations rather than trusting a client calendar.
  4. Every migration, booking decision or material change, and administrative asset change produces an append-only audit event.

**Plans**: 3 plans completed

### Phase 4: Public Discovery & Booking Requests

**Goal**: Let visitors confidently discover privacy-safe availability, request a room or dormitory, and track the resulting request.
**Mode:** mvp
**Depends on**: Phase 3
**Requirements**: ASSET-04, BOOK-01, BOOK-02, BOOK-03, BOOK-04, BOOK-05
**Success Criteria** (what must be TRUE):

  1. A visitor can browse rooms and dormitories and filter privacy-safe availability by type and requested date/time.
  2. A visitor can submit an accessible, responsive room request containing the required requester, purpose, attendance, asset, date, and time details.
  3. A visitor can submit an accessible, responsive dormitory request containing required stay dates and requester details.
  4. Invalid fields, dates, times, capacity, operating availability, and closures are explained before a request is accepted.
  5. A valid submission receives a non-guessable reference and pending confirmation, which a visitor can use to view only that request's privacy-safe status.

**Plans**: 3 plans completed
**UI hint**: yes

### Phase 5: Administrative Decisions & Operations

**Goal**: Equip authorized administrators to assess requests, make accountable decisions, and operate from schedule, dashboard, and audit context.
**Mode:** mvp
**Depends on**: Phase 4
**Requirements**: FLOW-02, FLOW-03, OPS-01, OPS-02, OPS-04
**Success Criteria** (what must be TRUE):

  1. An authorized administrator can review pending requests with the relevant asset, schedule, requester, and conflict context.
  2. An authorized administrator can approve or reject a pending request, with a recorded explanation for every rejection.
  3. An authorized administrator can view dashboard summary counts and filter bookings by status, asset type, and date range.
  4. An authorized administrator can use an asset-centric calendar that includes booking and closure context.
  5. An authorized administrator can view audit history with the actor, timestamp, action, and affected-record context.

**Plans**: 3 plans completed
**UI hint**: yes
